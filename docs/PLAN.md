# 《DanMu》实现计划书

## 1. 项目目标

打造一款 **高完成度、可直接游玩的纵版东方风弹幕游戏原型**，目标特征如下：

- 具备完整的开始菜单、游戏内 HUD、暂停、结算与重开流程。
- 具备东方系弹幕体验的关键要素：
  - 高密度可读弹幕
  - 低速精确移动（Focus）
  - 自机射击、残机、炸弹（Bomb）
  - 擦弹（Graze）
  - 道具回收与火力成长
  - 多阶段 Boss 战与符卡感演出
- 在无外部美术资源的前提下，用 **程序化图形、粒子、UI、配色与节奏设计** 做出较高完成度。

## 2. 实现原则

- **先可玩，再扩充密度与演出。**
- **优先保证手感与可读性。** 弹幕数量可以高，但要避免纯随机和纯遮挡。
- **尽量模块化。** 从空白 Godot 工程起步，拆分为主控、玩家、敌机、Boss、弹幕、HUD、关卡导演等模块。
- **减少外部依赖。** 不引入外部素材包，尽量使用代码绘制实现。

## 3. 范围定义

### 3.1 本次交付包含

1. **主菜单与流程控制**
   - 标题界面
   - 开始游戏
   - 暂停/继续
   - 游戏失败
   - 通关结算
   - 最高分记录

2. **核心战斗系统**
   - 8 向移动
   - 高速/低速切换
   - 自机主射击
   - 火力等级成长
   - 残机与复活无敌
   - 炸弹清弹与保命
   - 擦弹判定
   - 分数与基础奖励规则

3. **敌人与关卡**
   - 多组杂兵波次
   - 不同运动轨迹与射击模式
   - 节奏化关卡导演
   - 杂兵掉落分数/火力道具

4. **Boss 战**
   - 入场演出
   - 多阶段 HP / 符卡式模式
   - 阶段切换清弹
   - Boss 血条与阶段名展示

5. **演出与反馈**
   - 程序化背景滚动
   - 命中/击破/清弹特效
   - 炸弹范围演出
   - 阶段提示、提示文本与 HUD 状态反馈

### 3.2 本次不做

- 联机
- 复杂剧情对话系统
- 资源加载器、关卡编辑器
- 外部音频/美术资源集成
- 多难度切换

## 4. 技术方案

### 4.1 引擎与结构

- 引擎：**Godot 4**
- 入口：`scenes/main.tscn`
- 脚本层次：
  - `scripts/main.gd`：主状态机、对象注册、碰撞管理、流程控制
  - `scripts/player.gd`：自机移动、射击、擦弹、Bomb 请求
  - `scripts/bullet.gd`：玩家弹/敌弹统一实现
  - `scripts/enemy.gd`：杂兵逻辑与开火模式
  - `scripts/boss.gd`：Boss 阶段控制与符卡模式
  - `scripts/stage_director.gd`：按时间推进波次与 Boss 出场
  - `scripts/hud.gd`：菜单/HUD/暂停/结算 UI
  - `scripts/background.gd`：滚动背景与星屑演出
  - `scripts/effect.gd`：爆炸、冲击波、清弹圈等特效

### 4.2 碰撞思路

- 不依赖复杂物理体交互，采用 **轻量手写圆形碰撞**：
  - 敌弹 vs 玩家 hitbox
  - 敌弹 vs 玩家 graze 半径
  - 玩家弹 vs 杂兵 / Boss
  - 道具 vs 玩家吸附/拾取
- 原因：
  - 更适合大量弹幕
  - 逻辑集中、便于调参与调试
  - 对空白项目更容易快速稳定落地

### 4.3 视觉风格

- 以 **深色宇宙背景 + 高饱和霓虹弹幕** 为主。
- 子弹、敌机、自机、道具全部使用程序绘制图形。
- 通过以下方式提升完成度：
  - 多层滚动背景
  - 不同形状的弹幕（针弹、圆弹、星弹）
  - 受击闪烁 / 击破爆散 / 清弹环
  - Boss 血条、阶段名、提示词

## 5. 玩法设计

### 5.1 玩家规则

- 默认 3 残机，3 Bomb。
- `Shift` 低速，显示精确 hitbox。
- `Z / Space` 持续射击。
- `X` 使用 Bomb：
  - 清除场上敌弹
  - 对敌人和 Boss 造成持续伤害
  - 提供短暂无敌时间
- 擦弹增加 `Graze` 与分数。
- 火力道具提升射击覆盖与集中度。

### 5.2 计分规则

- 击破杂兵：固定分数。
- 擦弹：小额加分。
- 回收点道具：按回收状态给分。
- 击破 Boss 阶段：阶段奖励。
- 保存本地最高分。

### 5.3 关卡结构

计划做成一关完整流程：

1. **开场适应段**：低压波次，帮助熟悉手感
2. **中段增压**：交错方向射击、扇形与环形弹
3. **终段压迫**：更高密度杂兵混排
4. **Boss 战**：3~4 个阶段，难度逐步抬升
5. **结算**：通关/失败反馈与重开入口

## 6. 实施步骤

### 阶段 A：框架搭建

- 配置窗口尺寸、主场景、输入映射
- 建立主节点、实体层、UI 层、背景层
- 跑通菜单 → 开局 → 回菜单 的最小流程

### 阶段 B：战斗核心

- 实现玩家移动/射击/低速/判定点
- 实现玩家弹和敌弹
- 实现基础碰撞、受伤、死亡与复活
- 实现分数、Bomb、Graze

### 阶段 C：关卡内容

- 实现 3~4 种杂兵行为模板
- 实现时间轴导演器
- 配置多轮敌群与节奏变化
- 打通杂兵掉落与回收体验

### 阶段 D：Boss 与演出

- 实现 Boss 入场
- 实现 3~4 阶段弹幕模式
- 实现阶段切换、血条、阶段名提示
- 加入更完整的特效反馈

### 阶段 E：打磨与验证

- 调整弹速、判定、火力成长曲线
- 调整 UI 信息密度
- 验证暂停、失败、通关、重开
- 进行基础运行测试

## 7. 完成标准

满足以下条件即视为本次目标达成：

- 能从标题界面进入游戏并完成一整局流程。
- 玩家拥有清晰可用的移动、射击、Focus、Bomb、残机系统。
- 关卡包含明确的杂兵阶段与 Boss 战。
- HUD、暂停、结算和最高分持久化可用。
- 整体视觉虽为程序化资源，但具备较强“可玩成品感”。

## 8. 当前执行决策

基于仓库现状（空白 Godot 工程），本次实现采用以下具体决策：

- 使用 **纯代码生成玩法对象与 UI**，减少空工程下大量场景资源编辑成本。
- 使用 **程序绘制 + 脚本调度** 替代外部素材依赖。
- 先做 **单关高完成度原型**，而不是多关低完成度堆量。
- 优先保证 **可运行、可通关、可反复游玩**，再追求素材规模。
